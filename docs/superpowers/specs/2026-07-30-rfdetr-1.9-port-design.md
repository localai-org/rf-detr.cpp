# RF-DETR 1.9 port design

Date: 2026-07-30
Status: approved, ready for implementation planning

## Background

The fork [`adithyab94/rf-detr.cpp`](https://github.com/adithyab94/rf-detr.cpp) is
10 commits ahead of `localai-org/rf-detr.cpp@main` with RF-DETR 1.9 support. This
spec covers porting the code and converter changes from that fork. It is not a new
model architecture: it is an upstream version bump plus three segmentation variants
that a block-count bug was hiding.

The fork's diff has two halves. The code half (~200 lines across `src/` and
`scripts/convert_rfdetr_to_gguf.py`) is in scope. The artifact half (regenerated
`accuracy_sweep.json`, `per_cell_latency.json`, README benchmark tables, MANIFEST
sizes, `publish_hf.py` checksum support) is the output of their own 44-GGUF
conversion run and is out of scope: we would want our own numbers from our own
hardware.

### The bug being fixed

`SegmentationHead.__init__` in upstream `rfdetr` constructs one `DepthwiseConvBlock`
per decoder layer. Per `scripts/convert_rfdetr_to_gguf.py:165-201`:

| Variant                  | Decoder layers | Seg blocks |
|--------------------------|---------------:|-----------:|
| seg-nano, seg-small      |              4 |          4 |
| seg-medium, seg-large    |              5 |          5 |
| seg-xlarge, seg-2xlarge  |              6 |          6 |

Our converter and loader hardcode 4. The comment at `src/rfdetr_model.cpp:353`
justified this as PyTorch "zip-of-shortest" semantics, but that reasoning is wrong:
PyTorch has 5 blocks *and* 5 per-layer query streams, so `zip` pairs all 5. The four
larger seg variants have been emitting masks computed from 4 of 5 (or 6) blocks.
This is incorrect output, not merely truncated output.

## Decisions

| Question | Decision |
|---|---|
| Scope | Code and converter only; no artifact regeneration |
| Pre-fix seg GGUFs | Clean break with an actionable error |
| Verification | Unit tests plus a real seg-medium PyTorch parity run |
| Attribution | Fresh commits with `Co-authored-by` for adithyab94, credited in the PR |

## Unit A — Segmentation head block count

Replace the hardcoded 4 with the model's decoder layer count in five places:

| File | Change |
|---|---|
| `scripts/convert_rfdetr_to_gguf.py:399` | `for b in range(4)` becomes `for b in range(dec_layers)` |
| `src/model_loader.cpp:649` | `expected_tensor_names` loops to `cfg.decoder.layers` |
| `src/segmentation.cpp` | `BlockW bw[4]` becomes `std::vector<BlockW>`; drop the `min(n_layers, 4)` cap and its `n_layers != 4` warning |
| `src/rfdetr_model.cpp:365` | pass `n_dec_layers` instead of `std::min(n_dec_layers, 4)` |
| `src/segmentation.hpp` | doc comment: blocks are per-decoder-layer, not fixed at 4 |

### Backward-compatibility guard

`model_validate_tensors` (`src/model_loader.cpp:674`) hard-fails on any missing
tensor. Once `expected_tensor_names` demands 5 or 6 blocks, the 16 already-published
GGUFs (seg-medium, seg-large, seg-xlarge, seg-2xlarge x 4 quants) fail with a
generic `missing tensor 'segmentation_head.blocks.4.dwconv.weight'`.

Add a `count_segmentation_blocks(const Model&)` helper that scans for
`segmentation_head.blocks.N.dwconv.weight`. Call it from `model_validate_tensors`
before the generic loop. If the count is below `cfg.decoder.layers`, fail with a
message naming the variant, both counts, and the remedy: the file was converted
before the segmentation-head fix, its masks are incorrect, and it must be
re-downloaded or re-converted.

Extracting the helper is what makes the guard unit-testable without fabricating a
GGUF fixture.

Return the existing `RFDETR_ERR_MODEL_LOAD`. `include/rfdetr.h:20` already documents
that code as "tensor binding or inventory (e.g. missing tensors)", the log message
carries the specificity, and adding an enum value would be a public-ABI change for
no gain.

Accepting these files instead of rejecting them was considered and rejected: it
would keep shipping known-incorrect masks to anyone who does not read warnings.

## Unit B — Preprocessing parity

RF-DETR 1.9 uses `F.resize(..., antialias=False)` at inference to match its
`cv2.INTER_LINEAR` training pipeline. Our `stbir_resize_uint8_linear` call selects
Mitchell/cubic filtering and rounds through uint8, which shifts borderline detection
scores.

Introduce GGUF key `rfdetr.preprocess.resize_mode` with values
`bilinear_no_antialias` and `legacy_stb`. **An absent key means legacy**, so every
existing GGUF keeps its current behavior and established outputs. An unrecognized
value is a hard `RFDETR_ERR_MODEL_FORMAT` failure.

- `src/model_loader.hpp`: add `bool preprocess_bilinear_no_antialias = false` to `Config`
- `src/model_loader.cpp`: parse the key after the existing mean/std parsing
- `src/image_io.hpp` / `image_io.cpp`: add a `bool bilinear_no_antialias` parameter to
  `rfdetr_preprocess`; new path does float bilinear with half-pixel source centers,
  edge clamping, and no uint8 round-trip; the stb path is preserved for legacy files
- `src/rfdetr.cpp:131`: pass `cfg.preprocess_bilinear_no_antialias`
- `scripts/convert_rfdetr_to_gguf.py`: stamp `bilinear_no_antialias` on new conversions

`rfdetr_preprocess` is declared only in `src/image_io.hpp`, not in `include/`, so the
signature change costs no public API break. Its only callers are `src/rfdetr.cpp` and
`tests/test_image_io.cpp`.

## Unit C — Converter checkpoint loading

Replace `torch.load(args.checkpoint, map_location="cpu", weights_only=False)` at
`scripts/convert_rfdetr_to_gguf.py:715` with `_safe_torch_load` from
`rfdetr.utilities.io`, gated by a new `--trust-checkpoint` flag for legacy
checkpoints the user fully trusts.

That import exists only in `rfdetr>=1.9`, so `scripts/requirements.txt` moves to
`rfdetr==1.9.0` (adding `sentencepiece==0.2.2`, which 1.9 requires). No 1.7
fallback shim: the converter becomes 1.9-only, which is the point of the change.

## Verification

**Unit tests.**

- `tests/test_image_io.cpp`: the existing legacy-path call gains the new `false`
  argument. Add a case for the 1.9 path using a 2x2 source upscaled to 3x3, with
  hand-computed expectations (center pixel is the mean of all four source pixels).
- New test for `count_segmentation_blocks` and the guard's rejection path.

**Parity.** `scripts/gen_torch_baseline.py` hardcodes `--seg` to `RFDETRSegNano`, a
4-block variant that by construction cannot catch this bug. Generalize it to accept a
seg variant, generate a seg-medium baseline under `rfdetr==1.9.0`, and extend
`tests/test_parity_segmentation.cpp` to exercise the 5-block path against real
PyTorch tensors. This requires a `.venv` (none exists locally) and a checkpoint
download.

This parity run is the acceptance gate for Unit A. No unit test can catch a dropped
block; only real weights can.

## Out of scope

- Re-converting or republishing the 44 GGUFs to `huggingface.co/mudler`
- The fork's regenerated `accuracy_sweep.json`, `per_cell_latency.json`, README
  benchmark tables, and 44-model parity matrix
- `publish_hf.py` checksum and model-card work
- The keypoint-preview head, which the fork also does not support

Documentation changes are limited to: variant list 8 to 11, the 1.9 preprocessing
note, the new converter flag in `docs/conversion.md` and `docs/finetuning.md`, and a
`models/MANIFEST.md` note that 16 seg GGUFs need republishing.

### Required follow-up

Re-converting and republishing seg-medium, seg-large, seg-xlarge, and seg-2xlarge
(16 GGUFs) is a real, separate task. Until it happens, users downloading those
variants hit the new error. Publishing to `huggingface.co/mudler` is outward-facing
and needs its own explicit go-ahead.

## Risks

**Unverified assumption about 1.9 preprocessing.** The fork asserts RF-DETR 1.9
resizes with no intermediate uint8 rounding. `torchvision.transforms.functional.resize`
on a uint8 tensor returns uint8; whether 1.9 converts to float first is not confirmed.
If the assumption is wrong, our new preprocessing path is subtly incorrect. Mitigation:
read the actual `rfdetr==1.9.0` source during implementation, with the seg-medium
parity run as the backstop.

**Rebase surface against the GPU backend.** The fork branched from the pre-GPU `main`.
`src/rfdetr_model.cpp` and `src/model_loader.cpp` both changed in the GPU work, so
these edits land on top of it rather than beside it.

**Q4_K on segmentation.** The fork's sweep reports Recall@IoU-0.95 as low as 0.125 on
seg-small Q4_K. We are not adopting their numbers, but if we later regenerate our own,
the Q4_K guidance in `models/MANIFEST.md` likely needs revisiting.
